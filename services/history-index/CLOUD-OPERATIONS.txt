XERIS CLOUD HISTORY ARCHIVE — REVIEW REQUIRED BEFORE DEPLOYMENT

This service owns only a derived SQLite database. It never signs, submits,
mutates source ledger/receipt state, restarts a node, or reads private keys.
Source canonicality comes from the unchanged local L1; v4 scrypt/Merkle/parent
commitments are independently recomputed, but consensus signatures, difficulty
and gap certificates are not independently revalidated here.

INSTALLATION INPUTS (operator-reviewed, not automated by this document)

1. Stage cloud_archive.py, history_index.py, wire.py and receipt_effects.py in
   root-owned /opt/xeris/history-index. No dependencies beyond Python stdlib.
2. Install a consistent SQLite BACKUP of the already verified public full-index
   as /var/lib/xeris-explorer-history/index.sqlite3, owned by xeris-archive. Do not copy a live
   SQLite database without its WAL; use SQLite backup. This directory must be
   separate from /var/lib/xeris/mainnet-v4 and contain no private keys.
3. The baseline must contain the original pinned block27,201 plus ledger_prefix
   byte/digest/count evidence from verified backfill/tail. initialize() verifies
   the baseline source bytes and derives a stable anchor1,000 records behind it.
   It cannot bootstrap an arbitrary SQLite database or silently accept another
   chain. The genesis roster file SHA and runtime roster commitment are pinned.
4. Review/adapt the example unit paths to the actual host. The unit reads source
   state as a separate xeris-archive UID under a read-only directory mount so
   atomic ledger replacement is visible. Give that UID only directory-search ACL
   and explicit read ACL on public ledger.dat/ruleset files; never default ACLs.
   Root must maintain the exact public ledger inode's read ACL after replacement
   using a reviewed metadata-only helper; unavailable access fails closed.
   The two private producer files and /proc are inaccessible. All writes
   are confined to the derived archive directory; no public node port is opened.
5. Start only after independent tests/review. Measure CPU, RSS, refresh duration,
   ledger read volume, and native RPC latency before enabling at boot. The
   example applies CPUQuota100% (one CPU), low CPU/I/O weight and512MiB memory maximum.

REFRESH / PUBLICATION

The worker waits5s between completed refreshes; refreshes never overlap. The
NYC two-CPU host now uses CPUQuota100%; half-CPU throttling had delayed
verification enough to exceed the unchanged120s anchor-freshness limit.
Measured generation intervals after adjustment were41.845–46.186s over four
refresh changes. Nice10, CPUWeight10, IOWeight10 and512MiB remain unchanged.
Confirm fresh checkpoints and native RPC responsiveness over at least two full
refresh cycles; slower cycles still fail closed instead of accepting old data.
Each refresh checks the stable
prefix digest, replays at most5,000 suffix records/128MiB, recomputes every v4
header/Merkle root, preserves parent continuity, and rehashes the captured
complete prefix. A partial trailing append is excluded. A second post-native-API
hash check detects source changes during live anchoring. Ordinary appends beyond
the captured prefix are allowed. Expect up to three streamed prefix reads per
refresh; verify their cost on the selected host. No request scans the ledger.

Suffix changes use only Index.replace_suffix inside one SQLite transaction
after a proven common ancestor. Publication includes a fresh completed-block
hash match with the SAME host's127.0.0.1:50008 API. Advancing the stable anchor,
updating all derived records, coverage and generation metadata commit together.
Independent read-only WAL snapshots keep HTTP history available during refresh.

If the stable prefix differs, native evidence is wrong/unavailable, or a bound
is exceeded, the entire candidate transaction is abandoned. The old published
history remains accessible with coverage.stale=true. The exact checkpoint gate
fails closed. An explicit reviewed rebuild/activation is required for divergence
below the stable anchor; never reset or repair L1 state from this service.

The canonicality age bound is120s and maxnative/disk tip difference100slots.
The native feed supplies up to100 blocks to retain completed overlap between
refreshes; every shared block still requires an exact hash and timestamp match.
Deep same-inode tampering is detected on refresh; this does not claim instant
defense against a privileged local writer between checks. Private keys and the
L1's own signed consensus remain the security boundary for block acceptance.

  /health
  /v2/block/slot/27201        Original pinned checkpoint, fresh local-node gate.
  /history/coverage
  /history/blocks[?cursor=...]
  /history/transactions[?cursor=...]
  /history/block/{slot-or-hash}
  /history/transaction/{signature}
  /history/address/{address}[?cursor=...]
  /history/accounts[?cursor=...]
  /history/search?q={slot-or-hash-or-signature-or-address}

Malformed pagination cursors return HTTP400. Cursors whose indexed snapshot
changed or disappeared return HTTP410; restart pagination from its first page.
An archive or database failure returns HTTP503 and is not treated as expiry.

The accounts route returns basis="earliest_indexed_activity", up to100 rows
{address, first_seen_slot, first_seen_timestamp_ms}, truncated, cursor,
snapshot_tip, coverage and generation. It combines transaction address-index
appearances and block proposers; it excludes the all-zero system address.
This is earliest INDEXED activity, not wallet creation, total account population,
proof of successful transfer execution, genesis allocation or current balance.
Missing timestamps are null. Existing address-coverage limits still apply.
Rows sort by earliest slot, then address. A cursor retains its original tip even
after later appends; reorgs invalidate it. Stale history is returned with its
honest coverage.stale value, rather than inventing fresh timestamps.
Each request uses a read-only SQLite snapshot and caps work at2s/5million VM
instructions and101 retrieved rows. Budget exhaustion returns503 without
invalidating the separate checkpoint gate. The initial50,257-block public
baseline returned6 addresses in0.106s/1.659million VM instructions on the Mac.
Measure the deployed host. If future data growth reaches these bounds, add a
separately reviewed derived address index; do not remove request work limits.

Requests choose no path, source URL, network, key or database. Bind a reviewed
reverse proxy to only these public routes; preserve the frontend's exact fixed
checkpoint and separate Testnet route. Do not proxy arbitrary node control APIs.
The checkpoint response includes public transaction membership/instructions;
membership alone is not an execution-success receipt. Previously verified
receipt outcomes are retained for unchanged records; newly indexed outcomes
remain unknown until verified execution evidence is available. The background
refresh now checks up to 4 unknown transactions (including older rows) within a
4-second batch. A persisted descending cursor rotates past missing/invalid
receipts rather than retrying only the newest entries. Each fixed local child
has a maximum 1-second wall deadline and bounded response bytes; it calls only
getTransaction and that transaction's exact block-detail route on the SAME
127.0.0.1:50008 node. No public input chooses an RPC host/method/source path.

An imported receipt must match the stored full signature list, slot, every
instruction's indexed boolean outcome, error status, and canonical block
hash/Merkle root/complete ordered membership. Only outcomes and canonical-block
provenance are imported; unvalidated receipt summary effects/addresses are not.
The captured source prefix is rehashed after these calls and before the derived
transaction commits. Receipt updates, coverage and canonical generation publish
together. Receipt absence, malformed evidence, child timeout or the optional
query's 500,000-VM-step/time bound leaves outcomes unknown; it does not turn them
into failed transactions or prevent a valid canonical generation from publishing.
Coverage includes bounded receipt_refresh telemetry. Existing verified outcomes
survive unchanged ledger refreshes; orphaned rows are removed on verified reorg.

The native getTransaction RPC searches its recent in-memory block window. Old
unknowns whose transactions have aged out can remain unknown even if persistent
receipt records exist. Recover those with the existing reviewed snapshot-receipts
and receipt-import tools: read only the PUBLIC receipt SQLite schema, take a
consistent SQLite backup (including WAL state), and import only after its tip
hash is present in this verified index. Use an operator-controlled temporary
snapshot; no persistent broader node-directory ACL is required. Do not copy a
live SQLite file directly, guess success from inclusion, or alter L1 state.
